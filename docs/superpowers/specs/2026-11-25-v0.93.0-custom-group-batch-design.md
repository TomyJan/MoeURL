# v0.93.0 自定义组批量成员迁移设计

## 目的与选择

v0.92 已允许单账号加入自定义组，批量入口仍只能处理 user／admin。沿用 v0.30 入口和事务扩展可分配组，避免管理员为同一当前列表重复单条确认。本设计由 Agent 根据长期自主开发授权选择，不声称用户逐项指定。

比较新建 custom-only 批量 API、客户端循环旧单账号 API、扩展原原子批量 API：选择第三种。第一种重复协议，第二种无法保证全批回滚；第三种保持旧客户端与 builtin 行为，并复用既有数据模型、权限、审计及无缓存解析。

## 服务端契约

输入仍为 `{items: [{id, expectedUpdatedAt}], groupKey}`，返回 `{changedCount, unchangedCount}`。长度 1–100，重复／非规范 UUID 与无效时间在访问数据库前拒绝；目标 key 必须非空且非 guest，存在性和 builtin 标志由数据库判定。自定义 key 是不透明字符串，不从格式推断授权。

五秒 `WithAuditTx`：先 `LockGroupChangeUsers` 按 UUID 排他锁定 actor 与目标；锁 builtin admin 并从当前数据库重查 actor 活动状态、非 builtin 账号及 admin:access。保留原稳定错误类别优先级（缺失／删除、builtin、自身、不可分配源组、版本）。以已有 `GetUserGroupByID` 读取每个唯一源组，复用 `isAssignableGroup` 校验；持有账号锁时源组删除不可能成功，因为现有 FK 与有成员拒删。源组只读，不为成员出组争用额外多组排他锁。

版本全部通过后，`LockUserGroupForCustomManagement` 排他锁定统一目标，复用 `isAssignableGroup` 拒绝 guest、伪 builtin 和保留 builtin key。先前 admin 授权锁维持一致的 admin→目标次序。组删除若先完成则无效输入；迁入先锁定并提交则删除必须看到引用并拒绝。不引入 SQLC 查询或手工生成代码。

只有实际不同的 group_id 执行现有 `ChangeAppUserGroup` 与 `RevokeGroupChangeSessions`；审计 trigger 与账号更新同事务。当前同组不改变版本／会话／审计，陈旧同组仍冲突。提交前故障、取消或审计失败使事务回滚并返回零计数；但 `COMMIT` 响应丢失时，`WithTx` 仍可返回错误而数据库可能已经提交。因此 service 对任何错误返回零计数不等于证明回滚。前端把网络错误和异常响应视为结果不确定：清空冻结批次、读回账号与组目录；不得自动重放写入。身份与 Session 模型、域名及短链归属保持。

## 前端与失败状态

复用 AdminUsersPage 已有身份／epoch 组目录查询，传入批量 hook 的可分配 key 与目录 ready 状态。资格仅限真实目录内非 guest 组的可见非 builtin 非自身账号。目录 pending/error/fetching 时禁止新增选择／打开／提交；允许普通取消，提供明确的目录失败提示和重读。写后成功或受保护拒绝读屏障同时刷新目录与账号；任何一个失败屏障保持，显式重试只重读，不重放写入。

打开确认时复制账号和组 key／name 列表，传给对话框；目录刷新不重命名或自动切换冻结目标。用户显式改选后撤销确认。`submit` 使用当前目录重新检查目标仍可分配，但不能用重新读取替换原账号版本。服务端因目标删除返回 100001 时，沿现有 rejected 路径关闭快照并重读。每次 mutation 和读回都继续检查身份轮次，旧请求不得向新账号发布 toast、列表或草稿。

对话框按冻结目录显示源组与目标名。admin 目的保留提权 warning；其他组显示当前选中名称及全体实际变化者需重新登录的说明。未知源组用原 key 文本兜底，不能被误显示为 User。使用已有 Vuetify、TanStack Query、vee-validate、zod 与双语资源，无新依赖。
