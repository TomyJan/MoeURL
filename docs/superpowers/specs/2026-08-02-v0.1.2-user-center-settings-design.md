# v0.1.2 个人设置基础闭环设计

## 1. 背景

MoeURL 已完成控制台个人概览、短链管理、短链统计和前端主题偏好基础能力，但当前用户仍缺少一个明确的个人设置入口。登录用户可以看见自己的工作台，却不能在同一条路径里修改昵称，也没有一个专门承载账号信息和偏好的页面。

本设计在不引入系统设置、头像上传或服务端偏好同步的前提下，补齐个人设置基础闭环，让用户可以从首页和控制台进入自己的账号页，并完成最小可用的资料修改。

## 2. 设计目标

- 提供一个稳定的个人设置页，承载当前账号信息和最小资料编辑。
- 允许当前用户只修改自己的昵称，不碰用户名、状态、用户组和权限。
- 继续复用现有 `PreferenceSwitcher`、`auth/me` 和控制台 Shell，不重复实现偏好系统。
- 让首页账号入口和控制台账号入口都能进入个人设置流程。
- 保持页面在桌面端和移动端下都可用，并保持既有主题和国际化基线。

## 3. 非目标

- 不实现头像上传。
- 不实现密码修改。
- 不实现默认域名、默认跳转方式、时区或时间格式的服务端持久化。
- 不实现服务端语言和主题同步。
- 不实现系统设置表单、管理员仪表盘或 OIDC 配置。
- 不新增数据库表或迁移。

## 4. 方案选择

### 4.1 只做前端本地设置页

该方案可以最快上线，但只能展示账号信息，昵称无法回写到后端，页面会成为一个“看起来能改、实际上改不了”的壳，不符合个人设置页的最小闭环目标，因此不采用。

### 4.2 追加完整用户资料模型

该方案会把头像、时区、时间格式、默认域名和默认跳转方式一并纳入数据库和 API，范围过大，也会把当前版本拉向系统设置和账号管理的交叉地带，不符合当前版本边界，因此不采用。

### 4.3 追加自助昵称更新 + 复用现有偏好控件

该方案只补一个当前用户昵称更新接口，再把现有语言和主题控件放进个人设置页，既有真实可编辑能力，又不会引入新的持久化模型。本设计采用该方案。

## 5. 后端设计

### 5.1 API 契约

新增：

```text
POST /api/v1/user/profile/update
```

请求示例：

```json
{
  "nickname": "Alice"
}
```

成功响应沿用现有用户模块的统一响应体，返回更新后的用户摘要。

### 5.2 权限

- 服务层只允许当前登录的非 `guest` 用户修改自己的昵称。
- 不允许修改他人资料。
- 不允许通过该接口修改用户名、用户组、状态、密码或权限。
- 权限不足返回 `200` 和统一业务错误码，基础设施错误返回 `500`。

### 5.3 数据访问

当前 `app_user` 表已经具备 `nickname` 字段，无需 schema 变更。实现上新增一条 SQLC 更新查询，只更新当前用户的昵称和 `updated_at`，并保持 `deleted_at is null` 与 `builtin = false` 约束。

设计上优先复用 `internal/user` 模块中现有的用户摘要和错误映射，不新增独立 profile 模块。

### 5.4 错误处理

- 昵称为空或全空白，返回请求参数错误。
- 当前用户不存在、已删除或是内置只读账号，返回业务错误。
- 数据库或事务失败，返回 `500`。

## 6. 前端设计

### 6.1 页面结构

新增 `/profile` 页面，页面内容按以下顺序组织：

1. 账号概览卡：头像首字母、用户名、昵称、用户组。
2. 昵称编辑区：输入框、保存按钮、保存成功反馈。
3. 偏好区：复用现有语言和主题切换控件。
4. 快捷入口：进入控制台概览、我的短链和访问分析。

页面不展示伪数据，不展示未实现的头像上传、密码修改或系统设置表单。

### 6.2 数据流

页面使用 `auth/me` 作为当前账号数据来源，保存昵称时调用自助更新接口。更新成功后刷新 `auth/me` 缓存，让顶部头像、控制台账号卡和个人设置页保持一致。

语言和主题继续通过现有前端偏好系统写入本地存储，不新增后端依赖。

### 6.3 入口与导航

- 首页账号入口跳转到个人设置页。
- 控制台侧边栏增加「个人设置」入口。
- 移动端抽屉与桌面端导航共享同一入口结构。

### 6.4 页面状态

- 加载时显示固定尺寸的骨架屏或占位卡，避免布局跳动。
- 更新失败时只影响昵称保存区，不遮蔽账号信息和偏好区。
- 保存成功后给出明确反馈，并保持当前页面状态。

## 7. 测试策略

### 7.1 后端

- SQLC 测试覆盖当前用户昵称更新、非目标用户隔离、内置账号约束和空白输入。
- Service 测试覆盖权限检查、输入校验和查询结果映射。
- Handler 测试覆盖成功响应、业务错误和系统错误。
- 路由测试确认接口路径和 HTTP 方法正确。

### 7.2 前端

- API 测试确认请求路径、请求体和响应映射。
- 页面测试覆盖加载、成功、错误、空昵称校验和保存后刷新。
- 路由测试确认 `/profile` 正确挂载。
- 控制台 Shell、首页和翻译测试确认入口和文案一致。

## 8. 验收标准

- 当前用户可以进入个人设置页并看到自己的账号信息。
- 当前用户可以修改昵称，刷新后仍然生效。
- 语言和主题切换继续可用，并与现有前端偏好系统一致。
- 访客、无权限用户或其他账号不能修改当前用户资料。
- 后端和前端全部质量门禁通过。
