# v0.94.0 多组补充授权实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 subagent-driven-development（推荐）或 executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法跟踪进度。

**目标：** 在保持一个主组和旧 API 兼容的情况下，为普通持久化账号提供可 CAS 更新的自定义补充组，并让后端授权、用户界面和域名可用性一致采用当前数据库组集合。

**架构：** 新建 UUID 外键关联表承载完整补充组集合；写入以目标账号版本为 CAS，在单事务中替换关联、推进版本、撤销会话并审计。数据库权限 Resolver 按账号 ID 读取主组和所有补充组，生产业务逐项授权使用该快照；前端仍以单个主组字段为兼容显示，并增加稳定排序的补充组字段和冻结确认流程。

**技术栈：** Go 1.26.8、Chi、SQLC、Goose、PostgreSQL、Vue 3、TypeScript、Vuetify 4、TanStack Query、Vitest、Playwright。

**规格：** [范围](../../product/scope-v0.94.0.md)、[设计](../specs/2026-11-26-v0.94.0-supplemental-user-groups-design.md)。

## 审查重点与输入边界

- builtin **账号** 仅按 `app_user.builtin=true` 拒绝；普通持久化账号可使用 admin 主组并成为成员目标，操作者自身仍不可被管理。
- 空数组是明确清空；缺失、null、重复、主组重复、builtin／guest 组、未知组或非规范 key 必须在写事务前拒绝。
- 同值 CAS 先验证完整版本；陈旧版本不因目标集合相同而成功。真正 no-op 不推进版本、不撤销 session、不审计。
- 缺组、非法权限 JSON、账号状态异常或读取失败均不得退化为部分权限；`admin:access` 等 protected 权限不得从补充组获得。
- 主组和补充组显式域名 grant 与 permission 取并集；组默认值仅看主组，并保持个人默认／全局 fallback 顺序。
- 任一真实成员关系变化的关联替换、版本、会话撤销和审计须整体提交；回滚测试验证真实 PostgreSQL 中零部分写。
- 账号／组删除与成员新增、成员替换并发须以条件同步和锁跟踪验证，无固定 sleep。
- 网络、畸形响应、读回失败或身份轮次变化后，前端必须清理冻结目标并停写，显式刷新后才可重新选择，不重放不确定写请求。
