## 3. 实施阶段

1. 通过 Goose migration 和 SQLC 扩展短链访问配置，并同步内置权限。
2. 扩展创建、编辑、列表和响应契约，完成权限与时间校验。
3. 将公共访问拆分为初次打开、公开预览和最终继续，保持成功访问事件口径。
4. 在前端交付高级创建设置、共享配置对话框、中间页和二维码工具。
5. 修复既有 E2E 退出竞态，补齐 v0.2.0 E2E、覆盖率、构建分块和部署验证。
6. 更新任务与验收证据，完成最终审查和本地原子提交。

## 4. 技术要求

- 后端继续使用 Go、Chi、SQLC、Goose 和 PostgreSQL，不引入 ORM。
- 数据库新增 `redirect_mode`、`intermediate_delay_seconds` 和 `expires_at`，既有记录必须通过默认值保持兼容。
- 新增固定路由 `/go/{slug}` 和 `/go/{slug}/continue` 时，必须同步短码保留规则。
- 进入中间页不记录 `redirect_response_sent`；最终目标跳转成功写出后才计入访问量。
- 前端继续使用 Vue 3、TypeScript、Vuetify 4、TanStack Query、`vee-validate`、`zod` 和 vue-i18n。
- 二维码使用 `qrcode` 生成 PNG Data URL，不新增后端图片接口或持久化。
- 路由级页面使用动态导入，统计图表和二维码依赖不进入首屏主分块。
- 所有新增生产代码遵循 TDD，覆盖率不得通过降低阈值或无意义断言维持。

## 5. 验收重点

- 升级后的既有短链仍直接跳转，新增模式和过期时间有完整权限边界。
- 中间页展示、倒计时、立即前往、二次状态检查和统计事件口径一致。
- 状态切换不会覆盖访问配置，清除过期时间必须显式表达。
- 二维码编码内容严格等于短链 URL，生成失败不会展示空白图片。
- Playwright 退出流程使用条件等待，不使用固定延时。
- 后端、前端、覆盖率、构建和 Docker E2E 全部门禁通过。

## 6. 提交策略

按以下原子边界提交：

1. 版本范围与设计。
2. 实施计划与技术基线。
3. 数据库与访问配置领域模型。
4. 公共中间页访问链路。
5. 前端访问配置创建与编辑。
6. 二维码与公共中间页界面。
7. E2E、构建与发布验收收尾。

本地原子提交为默认收尾动作；`push`、合并及其他 Git 或远程集成操作仅在用户明确授权后执行。
