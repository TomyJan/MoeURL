# 技术选型决策

## 1. 决策结论

MoeURL 采用以下技术栈作为 v0.0.1 及后续演进的技术基线：

```text
后端：Go 1.26.8+ + Chi + SQLC 1.30.0 + Goose + PostgreSQL
前端：Vue 3 + Vite + TypeScript + Vuetify 4
前端包管理： pnpm
状态：Pinia + TanStack Query for Vue
国际化：vue-i18n
表单校验：vee-validate + zod
PWA：Web App Manifest + Service Worker
测试：go test + testify + testcontainers-go + Vitest + Playwright
部署：Docker + Docker Compose + 单 Go 服务托管前端静态产物
```

这套技术栈的目标是：稳定、现代、低魔法、易自托管、便于长期维护，并能支撑 MoeURL 后续权限、统计、多域名、跳转页模板和外部登录等扩展能力。

2026-10-27 的[开发依赖安全维护](2026-10-27-frontend-security-dependencies-plan.md) 选择同主版本 Vitest／coverage 补丁，以及原 testing-library 版本下的兼容子树刷新，清除 mocker／source-map-js／ini 公告；不新增 override 或手改锁文件，也不提高业务版本。传递 test-utils／beautifier 的升级和完整门禁单独留证，不把开发工具公告说成生产 HTTP 可达漏洞；生产镜像在新依赖冻结后重新构建和扫描。

## 2. 选型原则

v0.26.0 的[个人默认域名设计](../specs/2026-10-27-v0.26.0-personal-default-domain-design.md) 后端已完成本地验证：选择独立账号域名偏好资源及版本，避免更改 v0.15.0 完整替换请求或造成无关版本冲突；个人选择只影响创建面板初始值，保留后端省略 `domainId` 的全局默认语义。已新增关系表、标准 SQLC 查询与原域名删除事务内的偏好清理，不新增依赖、权限或默认策略框架；后端本地完整 Go／业务 100／vet／标准生成已通过，完整本地门禁已通过，独立整审和远端集成待完成。

技术选型遵循以下原则：

- **稳定优先：** 优先选择成熟、社区活跃、长期维护风险低的技术。
- **现代但不猎奇：** 使用现代开发体验和工程工具，但避免小众、不稳定或维护不确定的方案。
- **自托管友好：** 部署应尽量简单，适合个人和小团队维护。
- **低魔法：** 后端数据访问、权限判断和业务流程应清晰可审查。
- **长期可演进：** v0.0.1 不实现所有远期能力，但技术基线应能承接后续扩展。
- **UI 有设计感：** 前端避免通用后台模板感，优先贴近 Material Design 3 方向。

## 3. 后端技术栈

### Go

最低 Go 版本为 Go 1.26.8+；当前 `go.mod` 声明为 Go 1.26.8。

Go 作为后端语言，适合 MoeURL 的 API、认证、权限、短链跳转和后台任务场景。

选择原因：

- 单二进制部署友好。
- 运行稳定，资源占用低。
- 并发能力好。
- 标准库和服务端生态成熟。
- 适合自托管产品长期维护。

### Chi

Chi 作为 HTTP 路由和中间件框架。

选择原因：

- 轻量，贴近 `net/http`。
- 中间件模型清晰。
- 适合语义化 HTTP API。
- 不强加复杂框架结构。
- 便于在项目内部保持清晰模块边界。

### PostgreSQL

v0.22.0 批量归属转移沿用单条转移的模型、当前参与者校验和事务审计，不新增权限或表。最多 100 条在同一事务中按 UUID 顺序锁定，先检查全部数量及版本，再更新实际 owner 变化；选择全批成功或全批失败，避免离职移交时留下无法判断的部分结果。同 owner 仍校验版本，不制造审计；原地址、访问配置和全部历史事件不变。

v0.23.0 采用专用批量标签 API，复用内联 tags、元数据权限、当前列表选择和审计事务，不扩展通用批量编辑或集中标签库。用户及用户组共享锁后按 UUID 锁定短链，持锁重查权限、归属、完整版本与全部结果标签上限；仅实际 tags 变化写入单调版本和审计。个人私有列表 additive 返回完整 `updatedAt`，公开预览不增加版本。前端以冻结快照、显式确认、冲突刷新门闩和登录轮次隔离写入，不重试 mutation；无新 schema、权限或依赖。详细契约与证据见 [设计](../specs/2026-10-26-v0.23.0-batch-tags-design.md) 和 [验收](v0.23.0-acceptance.md)。

v0.20.0 单条短链归属转移复用 owner_id 与审计白名单，不新增 schema／权限。按用户 UUID、操作者组、短链的锁序在同一事务中重查授权及接收账号，完整精度 updated_at 防止陈旧移交；仅改变归属及单调版本，既有匿名统计随短链接管，公开地址和访问配置保持原值。同 owner no-op 避免无变化审计。

v0.19.0 用户组成员迁移复用 app_user.group_id 与既有审计触发器，不增加成员关系表或新授权层。按 UUID 顺序锁定操作者／目标，再从事务内数据库组读取管理权限；实际变更同时撤销所有旧 Session。选择完整精度 updated_at 乐观并发与同组 no-op，避免静默覆盖或无变化时强制退出。自定义组、多组和批量迁移仍单独规划。

PostgreSQL 作为主数据库。

选择原因：

- 关系模型成熟，适合用户、用户组、权限、域名和短链等核心数据。
- JSONB 能承载模板元数据、扩展配置和后续灵活字段。
- 统计查询能力强，适合后续访问数据分析。
- 自托管生态成熟。

v0.0.4 开始使用 PostgreSQL 持久化 `short_link_event` 访问事件表，用于支撑短链列表的总访问量、今日访问量和最近访问时间。v0.1.0 在事件表中追加 Referer 主机名、归类后的设备类型和可选国家代码，用于聚合统计；不保存 IP、完整 User-Agent 或完整 Referer。国家代码仅从部署者配置且由可信代理处理的请求头读取，不参与鉴权或安全决策。

v0.14.0 在既有匿名事件上增加有界 UTC 日期范围，复用 SQLC 聚合与现有索引，不引入统计仓库、预聚合表或新数据采集。选择最多 90 个连续日点，先范围过滤再维度聚合；保留全生命周期概览，单独返回区间总量，避免改变总访问量含义。日期范围不改变访问额度和最终跳转流程。

v0.2.0 在 `short_link` 增加跳转模式、中间页倒计时和可选过期时间。既有记录通过数据库默认值继续使用直接跳转，过期状态在访问时动态计算，不写回短链状态字段。

v0.3.0 在 `short_link` 增加 Argon2id 密码哈希、数据库失败窗口和密码更新时间，并新增短期访问授权表。授权令牌只以 SHA-256 哈希存储，公开访问通过 `HttpOnly`、`SameSite=Lax` 的 Cookie 传递，生产环境启用 `Secure`，TTL 为 15 分钟，并按短链限定为 `Path=/go/{slug}`；不使用 JWT 或登录 session 代替访客授权。解锁使用同源 `POST /go/{slug}/unlock`，短码由路径提供，请求体只传密码，使授权签发与后续预览、继续访问处于同一路径作用域。授权表分别按 `expires_at` 和 `short_link_id` 建立索引，支撑分批过期清理和短链删除时的级联行定位。失败窗口按短链行锁保护，保证多实例部署的一致性。密码失败次数约束先由 `00006` 以 `NOT VALID` 添加，再由 `00007` 独立验证，避免升级大表时在字段迁移事务中扫描全部历史数据。

v0.4.0 将确认页建模为第三种 `confirmation` 跳转模式，而不是独立布尔访问条件或确认令牌。该模式复用 `/go/{slug}`、同源预览和 `/go/{slug}/continue`，公开预览显式返回 `redirectMode`；前端状态机在 `intermediate` 模式进入自动倒计时，在 `confirmation` 模式等待访问者主动确认，在 `direct` 模式的密码解锁成功后立即进入 Continue 流程。三种模式遇到 `reason=continue-failed` 时均等待手动重试，不自动再次调用 Continue。migration 只扩展 `redirect_mode` 约束并追加 `short_link:use_confirmation` 权限，不新增确认状态字段；正常路径由 `00008 Up` 以 `NOT VALID` 完成约束替换，`00009 Up` 仅在旧约束仍残留时执行兼容性重试，`00010` 在独立 Goose 事务中验证，正常回滚仍在各阶段事务内保持原子性。确认点击属于非统计事件，最终访问量仍只统计成功写出的 `redirect_response_sent`。短链和用户管理生产 Service 共享数据库权限 Resolver，每次业务操作从 `user_group.permissions` 解析当前 `GroupKey` 的权限快照，不缓存跨请求权限，保证数据库撤权立即成为后端安全边界；任一 Service 缺少 Resolver 时均拒绝授权，不降级为静态权限。Continue 的未知基础设施错误通过 `reason=continue-failed` 回流到公共页面并重新读取最小预览，避免顶层导航落入纯文本 500，同时不把目标 URL 暴露给客户端。

v0.5.0 在现有 `user_group.permissions` 上实现内置用户组权限管理，不增加新的授权层或 schema 字段。服务端维护覆盖当前权限常量的稳定目录和三个静态预设，数据库仍只保存最终权限数组；`admin:access` 与三项全站短链管理权限固定属于 `admin`，防止管理员自锁和把依赖后台入口的无效组合授予其他内置组。匿名 `guest` 缺少可持久化所有者 ID，因此在访客短链归属和滥用防护实现前保持只读空权限，只允许编辑 `user` 和 `admin`。权限更新使用 `updated_at` 条件写入实现乐观并发，冲突拒绝覆盖；成功更新后的业务请求继续通过无跨请求缓存的数据库 Resolver 立即读取新权限。自定义用户组、成员迁移、多用户组和审计日志不进入 v0.5.0。

v0.8.0 在原有 `domain` 和 `short_link.domain_id` 上增加 `domain_user_group` 授权关系，不为个人或用户组引入默认域名字段。默认创建需要 `domain:use_default`，显式选择需要 `domain:use_assigned`；两者均与内置用户组对目标域名的授权取交集。管理员域名写入另需受保护的 `domain:manage` 和 `admin:access`。域名地址输入规范化为根 Origin，旧裸 authority 原样保留；同义地址冲突、乐观并发、默认切换和引用保护在事务中检查。公开访问从短链保存的域名构造 URL，并在每个访问入口按真实请求 `Host` 与启用状态重新校验，不以转发头扩大访问范围。`00013` 回填旧默认域名授权，不改写已发布短链；DNS/TLS 仍由外部代理提供。

v0.9.0 继续使用 `system_setting` 承载站点名称、默认语言、默认主题、纯文本页脚、Powered by 开关和本地登录策略，不引入第二张通用配置表。完整设置表单以 `site.settings_revision.updated_at` 作为统一乐观并发版本，并在单一事务中更新全部可编辑键。公开配置接口只暴露渲染所需的非敏感字段；本地登录状态只通过认证方式接口和受保护管理接口返回。

品牌署名在 v0.11.0 开发基线中固定展示；为兼容既有客户端和数据库，`site.show_powered_by` 及 API 字段继续保留，但读取和更新统一规范为 `true`，管理页不再提供开关。前端页脚的静态版本标识由构建时 Git 提交和精确匹配的语义化 tag 生成；Docker 构建通过 `MOEURL_BUILD_COMMIT` 与可选 `MOEURL_BUILD_TAG` 显式注入，不把 `.git` 历史放进镜像上下文，缺少完整提交时拒绝构建。

本地登录关闭与 OIDC Provider 变更共享数据库策略行锁。关闭本地登录、停用或删除 Provider 前，事务内必须确认最终集合仍至少包含一个运行配置完整且 Secret 可解密的 Provider；Discovery 等网络调用在加锁前完成，避免持锁等待外部服务。`system:manage` 与 `admin:access` 共同保护系统设置和 Provider 管理，前端路由与导航遵循同一权限组合。关闭开关不删除密码或撤销现有 Session，使管理员可以在保留已登录恢复通道的同时验证 OIDC；应用启动仍执行最终不变量校验，拒绝进入无登录入口状态。

v0.11.0 采用每条短链内的有界标题和 `text[]` 标签，不提前建立标签实体、用户标签库或额外服务。精确筛选使用 PostgreSQL 数组包含及 GIN 索引，关键词继续使用有界 SQL 文字匹配。元数据与原更新同事务写入，公开访问查询与返回模型保持独立，避免将管理分类信息暴露给访客。

v0.12.0 自定义短码沿用 `short_link.slug` 的全局唯一约束，在创建时一次性提交指定值，不增加可用性探测、额外预留表或短码修改接口。先验证原始 ASCII 再转小写，随机与指定值共用保留路由集合；冲突只依据 slug 唯一约束。独立权限与创建、域名授权在同一数据库事务中重查，权限 migration 使用 UPDATE 编辑追踪，只回收本次追加且未再修改的授权，不删除任何自定义短链。

v0.15.0 将账号语言与主题保存在专用 `user_preference` 表，使用受约束的可空字段表达未设置，不回填浏览器偏好。SQLC 条件写入以 `updated_at` 实现乐观并发；账号设置通过个人页明确保存，顶部切换继续属于浏览器即时选择。账号覆盖层不写入访客存储，身份改变时清除，避免跨账号继承。完整边界见 [账号偏好设计](../specs/2026-10-16-v0.15.0-account-preferences-design.md)。

### 聚合统计导出

v0.16.0 聚合统计导出采用服务端重新授权和同步 JSON 下载描述，复用现有最多 90 天的匿名聚合；浏览器只执行保存，不把旧缓存当作当前授权结果。标准库 CSV 负责转义，独立文本中和负责公式注入，固定字段名保持跨语言可分析。数据量已被趋势和维度上限约束，不增加队列、文件存储或第三方 CSV 依赖。

### 短链清单导出

v0.21.0 选择服务端同步、有界清单 CSV，复用既有下载描述与标准库 CSV，独立 `short_link:export` 叠加读取授权。单 SELECT 同时读取当前账号／组权限与清单，避免入口快照和多页拼接产生授权或归属漂移；不锁短链，也不追溯撤销已授权的在途读取。1000 条、累计原始可变长文本与最终 CSV 各 8 MiB 的双预算及 5 秒期限将成本保持有界。MATERIALIZED 候选集只保留最多 1001 条 ID／排序／字节数元数据，同语句检查条数和读取预算后才投影大文本，避免 SQLC 在最终 CSV 限制生效前累积不限长 URL。预算包含各 tag 元素及所属用户名，求和前转 bigint；极少规范化后缩小的集合也可能先被拒绝，不收紧既有 URL 写入兼容范围。超限要求缩小筛选，不静默截断或引入后台队列。

`00022` 沿用权限追加记录与 UPDATE-only 修订跟踪；Down 只撤销本次追加且未再独立修改的权限，保留既有授权与后续新组。不输出密码、哈希、授权令牌或原始访问事件，不改变统计导出的范围。

### 匿名访问记录导出

v0.24.0 采用单链、同步、有界 CSV，复用匿名成功事件和既有过滤／权限解析；独立导出能力叠加原读取与归属。同一 5 秒只读 repeatable-read 快照覆盖有效账号、当前组授权、未删除链接、数据库日期与查询，保持一份文件只有一个授权时刻。MATERIALIZED 候选最多 1001 条 ID／排序／bigint 文本长度，超过 1000 行或原文 8 MiB 时只返回无文本哨兵，通过预算才按候选 ID 回读；最终编码另限精确 UTF-8 8 MiB。避免浏览器拼页、全量 count、offset、N+1 和后台任务。

标准 CSV、BOM／CRLF、逐文本公式中和和严格 JSON 下载描述复用既有工具；机器字段、完整 UTC 时间与匿名空值不本地化。前端冻结已应用实际范围和过滤，以账号轮次、同步 cache 授权修订及父查询上下文阻止迟到下载，临时 Blob URL／节点始终释放。`00023` 只补内置组缺失导出权限并保留迁移后人工授权，无新事件字段、采集、索引或业务审计写入。规格和证据见[设计](../specs/2026-10-26-v0.24.0-visit-record-export-design.md)与[验收](v0.24.0-acceptance.md)。

### 操作审计导出

v0.25.0 选择管理员同步、有界 CSV，复用 audit_log 和列表过滤，不在浏览器拼分页、不新增采集或后台框架。独立受保护 `audit:export` 与 `admin:access`、`audit:read` 在同一 5 秒只读 repeatable-read 事务内重新授权；数据库时间和 180 天保留截止属于同一快照。MATERIALIZED 候选最多 1001 条，bigint 文本预算包含 changed_fields 的完整 JSON（含空元素、引号和分隔符），两级 8 MiB 限制在回读大文本及最终编码时分别执行，超过 1000 行或任一预算整体拒绝。

共享抽取仅限已有访问导出的有界 CSV buffer／公式中和，访问错误码 200120 不变，审计超限使用 100002。固定 11 列保留 bigint 字符串、UTC RFC3339Nano、空值与 JSON 数组；没有业务值或新索引。`00024` 只给 builtin admin 补缺失授权，以 UPDATE-only 修订追踪保留先有和独立编辑授权。前端复用原生下载、身份轮次和全局授权恢复；同步父级 contextRevision 覆盖全部草稿、范围／分页往返及查询状态。规格与精确证据见[设计](../specs/2026-10-27-v0.25.0-audit-export-design.md)及[验收](v0.25.0-acceptance.md)。

### 短链批量管理

v0.17.0 采用最多 100 条的同步、整批原子写入，复用现有个人／全站更新与删除权限，不增加后台作业或独立授权。单条 SQL 按稳定顺序锁定目标、重查当前账号与组授权，并用匹配数量保护全有或全无语义；避免客户端循环单条请求造成部分成功。前端只选择当前列表，删除确认保存快照，身份改变后不应用迟到结果。

批量写接口复用密码修改接口的 JSON 媒体类型校验，在解码前拒绝非 `application/json` 请求，封闭同站跨源简单请求携带 Cookie 的写入口；不引入新依赖或改变会话与权限模型。

### SQLC

v0.10.0 选择独立的有限额计数，拒绝使用异步统计事件作为额度权威，避免丢失事件和并发超发。有限额最终跳转在数据库短事务内持锁重检并领取；默认无限额保持原读路径。同一短链的领取串行，不同短链独立，域名共享锁允许并行读取。领取提交后不退款，优先保证严格上限；网络失败下额度用量可以高于成功记录的统计数。清除限额结束当前周期，不新增周期历史、后台任务或外部依赖。

SQLC 用于根据 SQL 生成类型安全的 Go 数据访问代码。自 v0.4.0 起统一使用 SQLC `1.30.0` 生成并校验代码。

选择原因：

- 查询明确，没有 ORM 隐式行为。
- 生成类型安全代码。
- 复杂查询可控，适合权限和统计场景。
- 与 PostgreSQL 和 Goose 配合自然。
- 更便于审查 SQL 性能和数据边界。

### Goose

Goose 用于数据库迁移。

选择原因：

- 简单、稳定、成熟。
- 支持 SQL migration。
- 与 SQLC 的 SQL 优先方式一致。
- 迁移文件易于审查和回滚。

### 认证与会话

v0.0.1 使用 Cookie Session + 服务端会话存储。

选择原因：

- 自托管 Web 系统更适合 Cookie Session。
- 服务端可主动撤销会话。
- 用户禁用、退出登录、权限变更后更容易生效。
- OIDC 外部身份登录继续绑定本地用户并签发现有服务端会话。

JWT 不作为 v0.0.1 的主会话方案。

v0.7.0 在该会话模型上实现多提供商 OIDC Authorization Code Flow。标准协议处理使用 `coreos/go-oidc` 与 `x/oauth2`，包括 Discovery、PKCE S256、签名、Issuer、Audience 和时间声明校验；业务层额外负责一次性 state、nonce、邮箱域名策略、外部身份绑定和本地用户状态。共享 OIDC HTTP Client 使用有界连接与响应超时，并拒绝自动跟随重定向，确保 Discovery、Token 和 JWKS 请求停留在已校验端点。Client Secret 与 PKCE verifier 使用部署级 AES-256-GCM 密钥加密，成功后仍签发 `moeurl_session`，不建立第二套会话或权限系统。

v0.13.0 的个人改密沿用 Auth Service 的 Argon2id、数据库失败窗口与两层并发槽位。用户行排他锁与 Login 的共享行锁使旧密码验证和 Session 提交同改密互斥；改密重新检查请求 Session 后，在同一事务更新哈希并撤销全部旧 Session。采用重新登录，避免第二套会话轮换协议；不新增权限、schema 或 OIDC 账号本地凭据，细节见 [设计](../specs/2026-10-15-v0.13.0-password-change-design.md)。

### 后端辅助库

v0.18.0 增加独立 `internal/insights`，使用现有 SQLC／PostgreSQL 快照提供全站聚合、匿名访问和审计查询，不引入外部统计平台。访问事件仅新增有界浏览器／系统类别，不保存原始 UA。全站多查询采用带 5 秒期限的只读 repeatable-read，分页使用 `(created_at,id)` 稳定 keyset，不增加全量 count 或无限区间。

关键变更审计采用应用显式 actor 上下文与事务局部 GUC、精确白名单触发器：同一事务保证业务与审计一起成功／回滚，避免跨服务遗漏字段快照及 best-effort 造成的不一致。手工改密事务保留错误计数提交协议；域名授权改为集合差量消除无变化噪音。审计不保存敏感值、不声明抵抗数据库管理员篡改；在线滚动保留 180 天，非空 Down 安全拒绝。备份与兼容 schema 回退独立于在线保留，设计见 [v0.18.0](../specs/2026-10-22-v0.18.0-analytics-audit-design.md)。

建议使用：

- `log/slog`：结构化日志。
- `cleanenv` 或同类库：配置读取。
- `argon2id`：密码哈希。
- `testify`：测试断言。
- `testcontainers-go`：PostgreSQL 集成测试。

## 4. 前端技术栈

### Vue 3

Vue 3 作为前端框架。

选择原因：

- 适合表单、列表、设置页和管理页。
- 组件模型清晰。
- TypeScript 支持成熟。
- 与 Vuetify 4、vue-i18n、Pinia 等生态配合自然。

操作反馈使用 `vue-sonner`，复用其通知堆叠、关闭、超时及可访问性支持。应用只挂载一个容器，页面级适配组件接入现有本地化消息；保留字段校验和持久重试区域，避免把可恢复状态仅放入短暂通知。

### Vite

Vite 作为前端构建工具。

选择原因：

- 开发启动快。
- Vue 支持成熟。
- 配置简洁。
- 现代前端项目主流选择。

### pnpm

pnpm 作为前端包管理器。

选择原因：

- 依赖安装快，磁盘占用低。
- 锁文件稳定，适合多人协作和 CI。
- 对 monorepo 和后续拆分扩展友好。
- 与 Vite、Vue 3 和 Playwright 生态配合自然。

### TypeScript

前端统一使用 TypeScript。

选择原因：

- 约束 API 响应结构。
- 降低权限、状态和表单字段错误。
- 便于长期维护。

### Vuetify 4

Vuetify 4 作为 UI 组件库。

选择原因：

- Vue 生态中成熟的 Material Design 组件库。
- 表单、导航、列表、弹窗、菜单和主题能力完整。
- 支持暗色模式和主题定制。
- 能避免 Ant Design 式通用后台风格。

使用约束：

- 不直接裸用默认主题。
- 应从前端初始化阶段建立 MoeURL 自定义主题，包括色彩、圆角、密度和暗色模式。
- 默认主题采用 Material Design 3 风格。
- 首页和短链访问页应更有产品感，避免做成传统后台页面。

2026-10-14 视觉更新继续使用 Vuetify 主题系统，集中维护雾蓝石墨配色、圆角和短时动效，不引入新的 UI 组件库。页脚归入唯一应用框架，避免各页独立占满视口后额外叠加页脚；视觉验证使用实际浏览器几何与颜色对比度，不保留镜像 CSS 字面值的脆弱测试。设计见 [视觉与交互规范](../specs/2026-10-14-ui-refresh-design.md)。

### PWA

v0.0.1 从前端工程初始化阶段支持 PWA 基础能力。

选择原因：

- 自托管短链系统常被移动端重复打开，PWA 可以改善启动和安装体验。
- Web App Manifest、图标和主题色属于低成本基础设施。
- Service Worker 可先用于 App Shell 和静态资源缓存，不影响业务数据一致性。

使用约束：

- v0.0.1 不缓存登录态 API、短链业务数据和权限相关响应。
- v0.0.1 不要求完整离线业务流程。

### 状态管理

v0.18.0 私有统计／日志继续使用 TanStack Query；query key 包含登录轮次、权限变化、资源、已应用日期、筛选和游标。访问记录与审计保留本地游标历史；切换后返回同一资源也启动新读取上下文，避免缓存和迟到响应恢复旧页。导航与路由使用相同权限交集。三个模块共用日期选择器并复用 Chart.js／Vuetify 标准表格，不引入新依赖；前端校验无效 envelope／DTO 时沿用数字 `ApiClientError` 契约。

前端状态分为两类：

- **客户端状态：** 使用 Pinia，例如当前用户、权限、主题、语言和全局 UI 状态。
- **服务端状态：** 使用 TanStack Query for Vue，例如短链列表、当前用户信息和管理列表。

不要把服务端列表数据长期塞进 Pinia。

### 表单和校验

使用 vee-validate + zod。

职责划分：

- zod 定义前端表单校验规则和类型。
- vee-validate 负责表单状态、错误展示和提交流程。
- 后端仍必须执行权威校验，前端校验只用于体验。

### 国际化

使用 vue-i18n。

v0.0.1 至少支持：

- 简体中文。
- 英语。

### 二维码

v0.2.0 使用前端 `qrcode` 库按短链公开 URL 即时生成 PNG Data URL。二维码不由后端生成或存储，不新增图片表、对象存储或二维码业务 API。

选择原因：

- 二维码是公开短链 URL 的确定性派生结果，无需服务端状态。
- 浏览器生成可以避免图片缓存、清理和部署存储配置。
- 成熟库负责二维码编码规则，项目只维护预览、下载和错误状态。

## 5. 测试技术栈

### 后端测试

后端测试使用：

- `go test`：标准测试入口。
- `testify`：断言和测试辅助。
- `testcontainers-go`：需要真实 PostgreSQL 的集成测试。

同一 Go 测试进程复用一个 PostgreSQL 容器；每个测试仍创建并清理独立数据库，兼顾隔离性与启动成本。

CI 的全仓普通测试与 race 测试使用 `-p=2` 限制同时运行的测试包，覆盖率保持 `-p=1`，避免多个 PostgreSQL 容器及 Docker 探测争用 runner。CI 设置 `MOEURL_TEST_REQUIRE_DOCKER=1`，Docker 失败直接报错，不回退到不存在的本地 PostgreSQL；不缩减测试范围或改变断言。

Docker 可用性探测采用轻量的服务端版本接口，并给予独立的 30 秒预算，避免冷启动时 `docker info` 的 10 秒超时使整包测试失败。使用真实 CLI 对受控 HTTP 端点回归成功与服务端失败，确保格式化输出不会将不可用服务端误判为可用；不增加自动重试或放宽覆盖率门禁。

测试重点：

- URL 校验。
- 短码生成和保留路径校验。
- 权限判断。
- 初始化流程。
- 登录和会话。
- 短链创建、禁用、软删除和访问。

### 前端测试

前端测试使用：

- Vitest：单元测试。
- Vue Testing Library：组件测试。
- Playwright：端到端测试。

Playwright 通过独立的 `setup` project 先完成一次初始化 UI 流程，再让业务 spec 并行执行；需要共享状态的受保护访问 spec 在文件内显式串行。

Playwright 默认使用隔离的 Docker Compose 环境。仅当 Docker Desktop 或外部镜像仓库不可用，且已保留原始失败证据时，才允许改用干净数据库、当前 Go 实现和当前前端产物运行同一套浏览器断言；回退不得掩盖应用构建、迁移或启动错误。

测试重点：

- 首页创建区域权限状态。
- 登录流程。
- 我的短链列表操作。
- 管理员全站短链入口。
- 多语言切换。
- 主题切换。

## 6. 部署技术栈

v0.0.1 推荐部署形态：

```text
浏览器
  ↓
Go 服务
  ├─ /api/v1/*       后端 API
  ├─ /assets/*       前端静态资源
  ├─ 固定前端路由     SPA fallback
  └─ /:slug          短链跳转
  ↓
PostgreSQL
```

生产环境优先提供 Docker 和 Docker Compose。

`Dockerfile` 的前端和后端构建阶段统一使用稳定镜像 `golang:1.27.3`，后端安全门禁使用 Go 1.26.10，消除标准库证书校验漏洞 [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809)。工具链补丁版本与最低语言版本分开管理，不改变 Go 1.26.8+ 的语言基线，但自行构建须使用对应 Go 分支的安全修复版本。生产镜像中的 Goose 使用独立临时 Go 模块构建，在固定 Goose v3.28.0 的同时固定 `golang.org/x/net` v0.60.0，使迁移工具与应用二进制遵循相同的已修复网络库下限。

Node 固定版本 tar 包继续从官方 HTTPS 地址取得，curl 使用 HTTP/1.1 和有界连接／传输超时及重试。此选择针对同一构建环境中默认 HTTP/2 完整下载停滞而 HTTP/1.1 完整传输成功的实际证据，避免无界等待；不采用镜像源、跳过证书校验或替代版本，应用运行时协议不受影响。

提交与 tag 注入仅由实际前端编译消费，将对应 ARG／ENV 放在依赖安装及源码复制之后、`pnpm build` 之前。依赖层不依赖提交标识，可跨原子提交复用；实际 bundle 仍按新提交生成并核对 footer，避免版本更新无谓重触发网络下载。

推荐方式：

- 前端使用 Vite 构建为静态资源。
- Go 服务在生产环境托管前端静态产物。
- API、前端页面和短链跳转由同一个 Go 服务处理。
- PostgreSQL 作为独立服务运行。

这种方式适合自托管用户，部署简单，也保留未来前后端分离部署的可能。

v0.6.0 将首个生产支持边界收敛为单机 Docker Compose + 外部 TLS 反向代理。默认 Compose 强制部署者提供数据库密码，PostgreSQL 不开放宿主端口，App 只绑定宿主回环地址并使用非 root、只读根文件系统、`tmpfs`、init、healthcheck 和重启策略。显式开发覆盖文件只恢复本机 PostgreSQL 直连，不弱化生产文件。反向代理负责 TLS、HSTS 和来源级限流；MoeURL 负责应用级请求防护、健康检查、优雅退出、初始化与登录保护。业务 API 统一返回 `Cache-Control: no-store`，静态资源保持独立缓存策略；单个 Auth Service 通过容量为 8 的进程内槽位限制登录事务，通过独立的容量为 2 的槽位只限制 Argon2id 密码验证，各层满额时复用登录限流错误并立即拒绝。该边界不承诺高可用、Kubernetes、内置证书管理或完整可观测平台，详细设计见 [v0.6.0 生产就绪设计](../specs/2026-08-29-v0.6.0-production-readiness-design.md)，运维入口见 [单机 Docker Compose 部署](../deployment/single-host-compose.md)。

## 7. 不采用的方案

### 不采用 Gin 作为首选路由框架

Gin 成熟且流行，但 MoeURL 不需要较重的框架式结构。Chi 更轻量，也更贴近 Go 标准库风格。

### 不采用 GORM 作为首选数据访问方案

GORM 使用广泛，但隐式行为较多。MoeURL 的权限、短链、统计和审计查询需要清晰 SQL，SQLC 更可控。

### 不采用 JWT 作为主会话方案

JWT 适合开放 API 和多服务认证场景。MoeURL 是自托管 Web 系统，Cookie Session 更适合用户禁用、登出、权限变更和已经实现的 OIDC 外部身份接入。

### 不采用 Ant Design 系 UI

MoeURL 需要更现代、更有产品感的界面。Vuetify 4 更贴近 Material Design 3 方向，符合项目视觉偏好。

### 不优先采用 SQLite

SQLite 对个人部署友好，但 MoeURL 后续会涉及访问事件、统计聚合、多用户管理和后台查询。PostgreSQL 更适合作为长期主数据库。
