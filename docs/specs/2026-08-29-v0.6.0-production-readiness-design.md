# v0.6.0 生产就绪设计

## 1. 背景

MoeURL 已完成到 v0.5.0 的产品功能闭环，但当前默认部署配置仍更接近开发便利性：数据库使用固定弱密码并映射宿主机端口，应用端口默认监听所有地址，健康接口不检查 PostgreSQL，进程入口也没有消费终止信号。应用已经具备 `App.Shutdown`，但正常主进程不会调用它。

本设计不继续增加短链业务能力，而是为个人和小团队的自托管场景建立第一个可验证的生产部署闭环。目标不是「任何规模生产环境」，而是一台受维护的 Linux 主机、Docker Compose、外部 TLS 反向代理和可恢复的 PostgreSQL 数据。

## 2. 方案比较

### 2.1 单个 v0.6.0 完成生产最小闭环

同一版本补齐进程生命周期、健康检查、Compose 默认值、初始化与登录保护、Session 清理、备份恢复和最小安全 CI。部署拓扑和验收目标只有一套，能够在发布时给出清晰结论。

### 2.2 先发布 v0.5.1 文档与 Compose 修正

先调整文档和端口默认值，再在 v0.6.0 实现安全与生命周期。单次变更较小，但中间版本仍缺少 readiness、初始化保护和优雅退出，不能宣称生产就绪，还会产生两套短期部署说明。

### 2.3 直接建设完整运维平台

同时实现高可用、指标、追踪、事件归档、备份调度和 Web 运维界面。能力更完整，但显著超出轻量自托管定位，数据模型和运维依赖也无法在一个小版本内可靠验收。

本设计采用方案 2.1。v0.6.0 只完成单机生产最小闭环，方案 2.3 中的能力保留为后续独立版本。

## 3. 可信边界与部署拓扑

```text
Client
  │ HTTPS
  ▼
TLS Reverse Proxy
  │ HTTP, loopback or private container network
  ▼
MoeURL App
  │ PostgreSQL protocol, private Compose network
  ▼
PostgreSQL
```

反向代理是公网边界，负责：

- TLS 1.2+、证书续期和 HSTS。
- 将应用上游固定到 `127.0.0.1:${MOEURL_HTTP_PORT}` 或同一私有容器网络。
- 覆盖客户端传入的转发头，只向上游写入代理自身确认的 `Host`、`X-Forwarded-Proto` 和来源信息。
- 对 `/api/v1/auth/login`、`/api/v1/init/setup` 和 `/go/*/unlock` 做来源级限流。
- 如配置 `MOEURL_ANALYTICS_COUNTRY_HEADER`，先删除客户端同名 Header，再由可信代理写入规范国家代码。

MoeURL 不根据 `X-Forwarded-For` 做安全决策。本版本不引入可信代理网段配置，避免错误信任任意来源头。

## 4. 配置与 Compose

### 4.1 配置契约

应用实际读取的环境变量为：

```text
MOEURL_ENV
MOEURL_HTTP_ADDR
MOEURL_DATABASE_URL
MOEURL_STATIC_DIR
MOEURL_ANALYTICS_COUNTRY_HEADER
MOEURL_SETUP_TOKEN
```

`MOEURL_ENV=production` 时，`MOEURL_SETUP_TOKEN` 必须至少包含 32 个字符。开发环境可以省略。`MOEURL_SESSION_SECRET`、`MOEURL_PUBLIC_BASE_URL`、默认语言和默认主题不属于当前应用配置契约，技术基线不得继续把它们列为已建议但未实现的部署变量。

Compose 额外读取部署插值变量：

```text
MOEURL_HTTP_HOST
MOEURL_HTTP_PORT
MOEURL_POSTGRES_PASSWORD
MOEURL_DATABASE_URL
```

`MOEURL_HTTP_HOST` 默认 `127.0.0.1`。`MOEURL_POSTGRES_PASSWORD` 和完整、已编码的 `MOEURL_DATABASE_URL` 都使用 Compose 必填插值，任一缺失时 `docker compose config` 和 `up` 必须失败。两者分别用于 PostgreSQL 初始化和 App 连接，避免把原始密码拼接进 URI；包含 URI 保留字符的密码必须只在连接 URL 的密码部分做百分号编码。

默认拓扑的 PostgreSQL 只位于受信单机私有 Compose 网络，明确接受内部链路使用 `sslmode=disable`。数据库链路经过不受信网络时，部署者必须通过同一 `MOEURL_DATABASE_URL` 选择 `sslmode=verify-full` 并提供匹配主机名的服务端证书和可信 CA；默认 Compose 不承担数据库证书和 CA 生命周期管理。

### 4.2 容器安全默认值

- PostgreSQL 只使用 Compose 内部网络，不声明 `ports`。
- App 映射 `${MOEURL_HTTP_HOST:-127.0.0.1}:${MOEURL_HTTP_PORT:-8080}:8080`。
- App 使用现有非 root 用户，并启用 `read_only: true`、`tmpfs: /tmp`、`init: true` 和 `restart: unless-stopped`。
- PostgreSQL 和 App 都设置 healthcheck；App healthcheck 请求 readiness。
- App 依赖 PostgreSQL healthy 后启动，entrypoint 继续先执行 Goose migration，再启动服务。
- 数据卷继续挂载 PostgreSQL 18 的 `/var/lib/postgresql`，普通重启和 `down` 不删除数据。

本版本不在 Compose 中内置反向代理。部署者可以选择 Caddy、Nginx、Traefik 或现有边缘代理，只要满足本设计的可信边界。

## 5. 应用生命周期

`cmd/server/main.go` 使用根 Context 组装应用，并在独立 goroutine 中运行 HTTP Server。主流程监听：

- `SIGINT`
- `SIGTERM`
- Server 非预期退出

收到终止信号后创建 15 秒关闭 Context，调用 `App.Shutdown`。关闭顺序固定为：

1. HTTP Server 停止接受新连接并等待在途请求。
2. 取消登录失败状态、Session 和短链授权清理任务。
3. 等待后台任务退出。
4. 关闭 PostgreSQL Pool。

即使 HTTP Server 关闭返回错误，也必须继续取消后台任务并关闭 Pool，再汇总返回错误。若关闭超时，记录 `server_shutdown_failed` 并以非零状态退出。正常信号关闭记录 `server_shutdown_complete`，不能把 `http.ErrServerClosed` 记为服务故障。

`App.Shutdown` 必须支持重复调用，不因 nil 后台任务或部分初始化状态 panic。应用初始化在创建 Pool 后执行带超时的 `Ping`；失败时关闭已经创建的 Pool 并返回带上下文的错误。

## 6. HTTP Server 与中间件

Server 使用以下基线：

| 配置 | 值 | 目的 |
| --- | --- | --- |
| `ReadHeaderTimeout` | 5 秒 | 限制慢 Header。 |
| `ReadTimeout` | 15 秒 | 限制完整请求读取。 |
| `WriteTimeout` | 30 秒 | 给静态资源和普通 API 留出稳定写出时间。 |
| `IdleTimeout` | 60 秒 | 限制空闲 Keep-Alive。 |
| `MaxHeaderBytes` | 1 MiB | 限制 Header 内存占用。 |

Router 中间件顺序为：

```text
Request ID
→ Panic Recovery
→ Security Headers
→ Request Logger
→ Request Body Limit
→ Health Routes
→ Current User（仅其余业务路由）
→ Business and Static Routes
```

健康路由必须在 `CurrentUserMiddleware` 之外注册。即使请求携带 Session Cookie，liveness 也不能触发 Session 查询或依赖 PostgreSQL。

Request ID 接受长度不超过 128 且只包含安全可打印字符的 `X-Request-ID`；无值或非法时生成随机 ID。响应返回最终 `X-Request-ID`，日志从 Context 读取同一个值。

Panic Recovery 捕获 panic，使用注入 logger 记录请求 ID、方法、路径和 stack，并返回 HTTP `500 + code=900000`。响应不包含 panic 值或 stack。

安全响应头至少包括：

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Frame-Options: DENY`
- 与当前 Vite/Vuetify 产物兼容的 Content Security Policy

`/api/v1` 下经过身份解析的业务响应统一设置 `Cache-Control: no-store`，包括 `GET /api/v1/auth/me` 等按 Session 返回数据的端点。静态页面和资源不套用该规则，继续使用现有静态文件缓存行为。

HSTS 只能由实际终止 TLS 的反向代理设置。应用不得在明文直连响应中盲目发送 HSTS。

非读取方法的请求体统一限制为 1 MiB。超限请求映射为通用无效请求，不允许 Handler 继续读取未受限 Body。当前产品没有文件上传，该上限不影响既有 API。

## 7. 健康检查

健康端点不要求登录：

```text
GET /api/v1/health/live
GET /api/v1/health/ready
GET /api/v1/health
```

`/live` 在 Router 能处理请求时返回 HTTP `200`、`code=0`、`status=ok`，不访问数据库。

`/ready` 使用不超过 2 秒的子 Context 调用 `pool.Ping`。成功返回 HTTP `200`；失败返回 HTTP `503`、`code=900000`、`status=unavailable`，并记录带请求 ID 的结构化错误。响应不暴露数据库地址或驱动错误。

`/health` 保留给现有脚本和部署，行为等同 readiness。应用未配置数据库依赖的隔离 Router 测试可以通过显式健康依赖测试 liveness，不得在生产装配中把 readiness 降级为固定成功。

## 8. 初始化保护

生产初始化 Token 是首次建站的部署凭据，不是登录 Session：

- 配置校验在 production 强制要求 Token。
- `GET /api/v1/init/status` 只返回 `initialized` 和 `setupTokenRequired`，不返回 Token 内容。
- `POST /api/v1/init/setup` 的请求体增加 `setupToken`。
- Service 在校验普通输入并确认系统尚未初始化后，使用常量时间比较验证 Token，再进入现有初始化事务。这样既保留现有输入错误和重复初始化语义，也不会让 Token 校验绕过一次性初始化边界。
- Token 错误使用稳定业务错误，不暴露正确值、前缀或长度。
- 初始化成功后，既有 `ErrAlreadyInitialized` 仍优先保证不能重复初始化。
- 前端只在 `setupTokenRequired=true` 时展示密码型 Token 输入；提交成功或失败后都立即清空局部值和 mutation variables，不能让 Token 留在 TanStack Query 状态中。

开发和 E2E 环境保持可选 Token。生产部署指南要求生成 Token、完成初始化并把 `.env` 作为敏感部署文件保护；即使初始化完成，后续升级仍应保留配置以满足 production 启动校验。

## 9. 登录失败保护

新增 `auth_login_attempt` 表：

```text
username_hash text primary key
failed_attempts smallint not null
window_started_at timestamptz not null
blocked_until timestamptz
updated_at timestamptz not null
```

`username_hash` 是服务端对裁剪首尾空白、保持大小写不变的登录用户名计算的 SHA-256 base64url 摘要。该规范与现有大小写敏感账号查找保持一致。表不保存额外明文用户名，不与用户表建立外键，因而已存在和未知用户名可以走同一路径。

登录流程：

1. 规范化用户名并计算摘要。
2. 非阻塞获取单个 Auth Service 容量为 2 的进程内登录准入槽位；满额时立即返回现有登录限流错误，不开启数据库事务，也不调用密码校验器。
3. 获得槽位后，在事务中锁定或创建尝试记录，读取数据库时钟和阻断状态。
4. 查询用户；不存在、无密码或异常账号都使用固定的有效 Argon2id 哑元哈希完成一次密码验证。
5. 凭据失败时更新 15 分钟窗口；第 10 次失败设置 15 分钟阻断。
6. 凭据正确但用户禁用时保留现有禁用语义，不创建 Session。
7. 成功登录时删除该摘要的失败记录并创建 Session，并在登录流程返回时释放准入槽位。

登录从事务 `Begin` 到 `Commit` 使用脱离请求取消、最长 10 秒的操作 Context。客户端断开不能中止已经开始的密码校验或失败状态提交。事务延迟回滚使用独立的最长 2 秒清理 Context，不能复用已经取消或超时的操作 Context；数据库、权限解码和随机数失败均保持原始错误链并回滚事务。公开密码校验器签名和现有 Session Service 事务边界不在本任务重构。

未知用户名、错误密码和密码为空统一返回 `110101`。阻断状态返回新的稳定登录限流业务码，响应不得说明用户名是否存在。数据库错误继续返回 HTTP `500`。

账号级限流不能替代来源级限流，因为攻击者仍可使用大量用户名。部署指南必须给出反向代理端点限流要求，但不把特定代理产品写成唯一实现。

`auth_login_attempt` 使用 `auth_login_attempt_updated_at_idx` 支持陈旧状态清理。每轮按 `updated_at`、`username_hash` 稳定排序并使用 `FOR UPDATE SKIP LOCKED` 选择最多 500 条记录，只删除同时满足以下条件的状态：

- `updated_at <= clock_timestamp() - interval '15 minutes'`
- `blocked_until is null or blocked_until <= clock_timestamp()`

这两个条件保留仍处于完整失败窗口内的记录和仍在阻断期的记录；已超过窗口且阻断期已经结束的记录可以删除。清理任务启动后立即执行一轮，随后每 15 分钟执行。每个周期只处理一个 500 行批次，不在单轮中持续排空；失败记录 `login_attempt_cleanup_failed` 和安全错误，不记录用户名摘要，并继续下一轮。任务收到取消后退出，由 App 统一等待完成。

登录失败状态清理不是 Session 清理。前者回收按用户名摘要聚合的安全临时状态，后者回收认证 Session，两者使用不同表、资格条件和查询。

## 10. Session 清理

新增 SQLC 分批删除查询，每次最多删除 500 条满足以下任一条件的 Session：

- `expires_at <= clock_timestamp()`
- `revoked_at is not null`

清理任务每 1 分钟执行一次，启动后先执行一轮。每个周期只处理一个固定上限为 500 行的批次；删除按可利用 `session_expires_at_idx` 的顺序和条件分批进行，如果执行一批后仍达到上限，可以在下一轮继续，不在单次任务中无限循环。

登录失败状态清理、Session 清理和现有短链授权清理由 App 统一持有取消函数与完成信号。正常错误记录事件名、任务名和错误，不包含用户名摘要、Session ID 或授权标识；错误只结束当前轮次，后续调度继续执行。

## 11. 运维流程

新增部署文档覆盖：

- 主机、Docker、Compose、域名和反向代理前置条件。
- `.env` 权限、数据库密码和初始化 Token 生成。
- 首次启动、readiness、初始化和 HTTPS 验证。
- Caddy 与 Nginx 的最小反向代理示例，以及必须自行配置的端点限流边界。
- PostgreSQL 自定义格式逻辑备份、校验、保留和隔离恢复。
- 升级前备份、`docker compose config`、镜像构建、migration、readiness 和回退判断。
- 主机丢失后的卷外备份恢复演练。

恢复演练必须创建隔离数据库或隔离 Compose project，并验证：

1. `goose_db_version` 等于目标版本。
2. 内置用户组和管理员记录存在。
3. 管理员可以登录。
4. 样例短链及其访问配置存在并可访问。

任何涉及 `docker compose down -v`、删除数据库或覆盖卷的命令都必须在文档中标记数据影响，并要求先确认目标 project 和备份。

## 12. CI 与供应链门禁

在既有 `Check Code` 工作流中增加独立安全任务，避免拖慢普通 lint 反馈：

- `go test -race ./...`
- 固定版本 `govulncheck ./...`
- 构建最终 Docker 镜像并使用固定版本扫描器扫描操作系统包和语言依赖中的高危、严重漏洞

扫描器数据库或外部服务不可用必须报告为基础设施失败，不能把扫描结果伪装为通过。对确需接受的漏洞必须记录漏洞 ID、影响面、补偿措施和复核日期，不提供全局忽略文件作为默认逃生路径。

Compose smoke test 从空卷启动，验证 readiness、生产初始化 Token、数据写入、应用重启后的数据保留和正常 `down` 清理。测试使用独立 project name，只有该 project 可以执行 `down -v`。

## 13. 数据迁移与回滚

登录失败表和 `updated_at` 清理索引通过新的 Goose migration 创建。Up 和 Down 均保持单事务；Down 只删除临时安全状态及其索引，不修改用户、Session 或短链数据。Session 清理只增加查询，不需要 schema 变更。

升级前必须备份。若应用代码回滚到 v0.5.0，新增登录失败表可以暂时保留而不影响旧代码；执行 migration Down 会丢失失败计数并解除临时登录阻断，这一影响必须写入 migration 测试和运维文档。

## 14. 兼容性与错误语义

- 既有 `/api/v1/health` 路径保留，但从固定进程状态提升为 readiness。
- 初始化请求新增字段只在 production 必填；development 旧请求继续有效。
- 登录成功、错误凭据和禁用账号的既有业务码保持不变，只新增限流码。
- 短链访问、权限、统计和公开预览契约不变。
- Compose 的 PostgreSQL 宿主端口兼容行为不保留在生产文件中；需要直接调试数据库时使用显式开发覆盖文件或独立命令，不在默认生产拓扑开放。

## 15. 测试策略

- Config：production Token 缺失、长度边界、development 可省略和空白规范化。
- Lifecycle：信号触发、正常关闭、超时、Server 提前失败、重复 Shutdown 和后台任务退出。
- Database：启动 Ping 成功与失败，资源失败路径关闭。
- Middleware：请求 ID 传递与替换、panic 恢复、日志字段、安全响应头、请求体上限和响应接口兼容。
- Health：live 不依赖数据库，ready 成功、超时和失败，兼容入口行为一致。
- Setup：production Token 成功、失败、不记录、不回显，development 兼容和重复初始化。
- Login：未知用户名哑元哈希、窗口边界、第 10 次阻断、成功清理、并发失败、多 Service 实例一致性、请求取消后的失败提交、基础设施回滚和有界事务清理。
- 登录失败状态清理：活动窗口保留、仍阻断记录保留、陈旧及阻断过期记录删除、500 行批量上限、启动立即执行、周期执行、失败后继续、取消退出，以及 App 启动并等待该任务。
- Session：过期、撤销、有效记录保留、批量上限、任务取消和错误不阻断。
- Compose：配置缺少密码时失败、端口边界、容器健康、重启保留、空库 migration 和初始化。
- Runbook：命令语法检查和隔离恢复演练。
- 回归：Go 全量、业务覆盖率、前端四项 100%、Playwright 全量、race、漏洞与镜像扫描。

## 16. 决策记录

- v0.6.0 的生产声明只覆盖单机 Docker Compose + 外部 TLS 反向代理。
- 默认安全优先于本地数据库直连便利性，PostgreSQL 不映射宿主机端口。
- 生产初始化必须使用部署 Token，开发环境保持低摩擦。
- 登录限流使用数据库共享状态，不依赖进程内计数或未经验证的客户端 IP。
- HSTS 和来源级限流属于 TLS 反向代理职责；请求 ID、panic 恢复和应用级安全校验属于 MoeURL 职责。
- 本版本不删除历史访问事件，避免累计访问量语义倒退。
- 产品总览和稳定规格中的远期能力仍不是当前实现承诺；最新 scope 和 acceptance 是版本完成状态的权威入口。
