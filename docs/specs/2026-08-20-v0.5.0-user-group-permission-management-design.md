# v0.5.0 用户组权限管理设计

状态：已于 2026-08-20 完成，本文档保留设计决策，实际验证结果见 [v0.5.0 验收清单](../implementation/v0.5.0-acceptance.md)。

## 1. 背景

本设计启动时，MoeURL 已经把权限字符串持久化在 `user_group.permissions`，Session 身份通过 `auth/me` 返回当前权限，短链和用户管理 Service 也共享数据库权限 Resolver；控制台的 `/admin/user/group` 仍是规划中占位页，管理员无法从产品界面查看或修改真实权限。

路线图在 v0.4.0 之后首先列出权限预设模型。v0.5.0 选择在现有单主用户组模型上交付内置用户组权限管理，不把用户组创建、成员迁移和多用户组关系混入本版本。

## 2. 方案比较

### 2.1 只读权限可视化

只展示数据库中的三个内置用户组和权限，不提供写入。实现风险最低，但不能兑现权限预设，也不能形成可管理闭环。

### 2.2 内置用户组权限编辑与预设

复用现有 JSONB 权限数组，展示三个内置用户组，并为 `user`、`admin` 提供目录化编辑、预设、后端校验和乐观并发。`guest` 在访客短链归属和滥用防护落地前保持只读。该方案不需要 schema 变更，可以直接利用现有动态 Resolver 保证更新即时生效。

### 2.3 完整自定义用户组

同时支持创建、删除、成员分配和权限编辑。该方案需要定义删除时成员迁移、默认用户组、用户改组、引用完整性和更多管理权限，超出一个最小版本的安全边界。

本设计采用方案 2.2。它可以替换现有占位页，同时把完整 RBAC 保留为独立版本。

## 3. 权限目录

服务端在 `internal/permission` 维护唯一权限目录。每项定义包含：

```go
type Definition struct {
	Key       string
	Category  string
	Protected bool
}
```

目录必须覆盖当前 13 个权限常量。API 只返回稳定 `Key`、`Category` 和 `Protected`，显示名称与说明由前端 i18n 维护。

分类如下：

- `short_link_basic`：创建、查看、更新和删除自己的短链。
- `short_link_access`：中间页、过期时间、访问密码和确认页。
- `domain`：使用默认域名。
- `administration`：后台入口和全站短链管理。

`admin:access`、`short_link:read_all`、`short_link:update_all`、`short_link:delete_all` 是受保护管理权限。服务端固定其归属：`admin` 必须拥有，`guest` 和 `user` 必须不拥有。保护规则只约束权限配置写入，业务 Service 仍按权限快照逐项授权。

`guest` 在 v0.5.0 固定为空权限集合，并在列表响应中标记为不可编辑。匿名身份当前没有可持久化用户 ID，短链 Service 也要求有效所有者 UUID；允许给 `guest` 套用业务预设会产生界面显示已授权但实际操作失败的假能力。访客创建、归属、配额和滥用防护必须作为独立闭环设计。

## 4. 权限预设

预设由服务端目录静态定义并随列表接口返回：

```text
restricted = []
basic = [
  short_link:create,
  short_link:read_own,
  short_link:update_own,
  short_link:delete_own,
  domain:use_default
]
standard = [全部可配置权限]
```

预设响应同时声明 `applicableGroups: ["user", "admin"]`。前端套用预设时只更新当前草稿，不立即发请求。保存请求提交完整权限集合，受保护权限按目标用户组基线保留。`guest` 只显示 `restricted` 状态，预设和保存控件禁用。服务端不接受客户端自定义预设，也不在数据库增加预设字段。

## 5. 后端架构

新增 `internal/usergroup` 包，保持职责独立：

- `model.go`：列表、目录、预设和更新输入输出模型。
- `service.go`：管理员授权、权限规范化、保护规则和并发更新。
- `handler.go`：HTTP 解码、业务错误映射和统一响应。
- 对应测试覆盖纯规则、数据库查询和 HTTP 契约。

Service 依赖 `permission.Resolver` 和 SQLC 查询。生产装配必须显式注入 `permission.NewDatabaseService(pool)`；缺少 Resolver 时按现有用户与短链 Service 的规则拒绝授权。

读取流程：

```text
请求 → 解析当前用户 → Resolve(GroupKey) → 检查 admin:access
     → 查询三个内置用户组 → 解析并规范化权限
     → 返回用户组、权限目录和预设
```

更新流程：

```text
请求 → Resolve(GroupKey) → 检查 admin:access
     → 拒绝 guest，校验 groupKey、expectedUpdatedAt、未知项和重复项
     → 校验受保护权限固定归属 → 按目录顺序编码 JSON
     → WHERE key + builtin + updated_at 条件更新
     → 返回更新后的用户组
```

一次业务操作只解析一次操作者权限快照。v0.5.0 不为 Resolver 增加缓存。

## 6. SQLC 与并发

`queries/user.sql` 增加：

- `ListBuiltinUserGroups`：按 `guest`、`user`、`admin` 的稳定顺序返回内置组。
- `UpdateBuiltinUserGroupPermissions`：仅在 `key in ('user', 'admin')`、`builtin = true` 和 `updated_at = expectedUpdatedAt` 同时匹配时更新。

更新时间使用 `greatest(clock_timestamp(), updated_at + interval '1 microsecond')`，保证成功写入产生严格递增版本。API 使用 Go `time.RFC3339Nano` 输出和解析 `updatedAt`，保留 PostgreSQL 小数秒精度，不能复用会截断精度的日期格式化函数。条件更新返回零行时，Service 再查询目标：不存在或非内置返回 `ErrUserGroupNotFound`，仍存在则返回 `ErrPermissionConflict`。

权限数组按目录顺序编码，避免同一集合因客户端顺序不同产生无意义变更。若规范化后的集合与数据库当前集合相同，仍允许保存并产生新版本，保持请求语义和冲突检测简单一致。

## 7. API 设计

### 7.1 列出用户组与目录

```text
GET /api/v1/admin/user-group/list
```

成功响应结构（数组内容节选）：

以下 JSON 仅展示字段结构。顶层 `groups`、`permissions`、`presets` 以及用户组和预设内的 `permissions` 数组均为节选，代码块内不使用省略号，以保持 JSON 合法。实际成功响应必须按稳定顺序完整返回 `guest`、`user`、`admin` 三个内置用户组、全部权限目录和 `restricted`、`basic`、`standard` 三个预设；各预设必须包含其完整的可配置权限数组。

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "groups": [
      {
        "key": "user",
        "name": "User",
        "description": "Default user group",
        "builtin": true,
        "editable": true,
        "permissions": ["short_link:create"],
        "updatedAt": "2026-08-20T00:00:00.123456Z"
      }
    ],
    "permissions": [
      {
        "key": "short_link:create",
        "category": "short_link_basic",
        "protected": false
      }
    ],
    "presets": [
      {
        "key": "basic",
        "applicableGroups": ["user", "admin"],
        "permissions": ["short_link:create"]
      }
    ]
  },
  "meta": {}
}
```

### 7.2 更新权限

```text
POST /api/v1/admin/user-group/update-permissions
```

请求：

```json
{
  "groupKey": "user",
  "permissions": [
    "short_link:create",
    "short_link:read_own",
    "short_link:update_own",
    "short_link:delete_own",
    "domain:use_default"
  ],
  "expectedUpdatedAt": "2026-08-20T00:00:00.123456Z"
}
```

成功响应只返回更新后的 `data.group`。错误映射遵循产品范围中的 `100001`、`120001`、`300201`、`300202`、`300203` 和 `900000`。

## 8. 前端状态与交互

新增 `AdminUserGroupsPage` 替换占位页。页面结构保持控制台现有工作型界面：

- 页头展示页面名称和用户组数量。
- 使用 Tabs 在三个内置用户组之间切换。
- 当前组展示基础信息、预设选择和按分类排列的权限复选框。
- 受保护权限保持可见，以禁用复选框表达固定归属。
- `guest` 的预设、权限和保存控件全部只读，并明确保持 `restricted`。
- 套用预设只修改草稿；保存按钮在草稿无变化、请求中或数据失效时禁用。
- 每个用户组维护独立草稿，切换 Tabs 不丢失尚未保存的编辑。

TanStack Query 使用 `['admin-user-groups']` 作为查询键。保存成功后以响应更新当前组，并刷新 `['admin-user-groups']` 和 `['auth', 'me']`。发生 `300202` 时丢弃冲突草稿、重新获取服务端状态并显示明确冲突提示，不自动重试写入。

页面覆盖加载、空列表、读取失败、保存失败、冲突和成功反馈。桌面端保持分类内容可扫描，移动端改为单列，不产生横向溢出；控件尺寸不因权限名称或状态变化导致布局跳动。

## 9. 安全与失败策略

- 前端不可决定哪些权限受保护，服务端对每次写入重新校验。
- 非管理员读取和写入都返回业务无权限，不泄露用户组权限配置。
- 未知权限、重复权限、空 `groupKey` 和非法时间均返回无效请求。
- 非内置用户组不能通过 v0.5.0 API 修改。
- `guest` 不能通过更新 API 修改；服务端不能仅依赖前端禁用状态。
- 冲突不能以最后写入者覆盖处理，管理员必须基于最新状态重新编辑。
- 数据库解析或写入错误返回 HTTP `500`，不得降级为静态权限或部分成功。
- 日志记录用户组标识、操作者 ID 和错误分类，不记录 Session、密码或其他敏感数据。

## 10. 测试策略

- 权限目录：权限常量零遗漏、键唯一、预设只引用可配置权限、适用组正确、受保护基线正确。
- Service：管理员授权、非管理员拒绝、`guest` 只读、未知与重复权限、保护规则、规范排序、组不存在和并发冲突。
- SQLC：稳定列表顺序、条件更新、严格递增 `updated_at` 和零漂移生成。
- Handler/Router/App：两个 API 路由、业务错误码、基础设施错误、生产 Resolver 装配和运行时撤权。
- Web：响应解析、独立草稿、预设套用、`guest` 只读、保护项禁用、保存状态、冲突刷新、`auth/me` 刷新和导航解除占位。
- E2E：管理员真实页面、`guest` 只读、修改 `user` 权限、普通用户能力即时变化、恢复基线，以及桌面和移动布局。

## 11. 决策记录

- v0.5.0 只管理三个内置用户组，不创建自定义用户组。
- 权限目录和预设由服务端定义，前端只负责本地化与交互。
- 预设不是新的授权层，数据库只保存最终权限数组。
- `guest` 在访客资源归属和滥用防护实现前保持只读空权限。
- 四项管理权限固定归属 `admin`，防止自锁和无效组合。
- 并发控制复用 `updated_at`，不增加 schema 字段。
- 权限更新后的请求直接读取数据库，不增加跨请求缓存。
