# v0.63.0 目标主机白名单设计

## 意图与边界

接续已交付的精确黑名单，让管理员显式收敛新目标的可用 DNS 主机。默认关闭；不改变已分发链接的访问、历史目标或其他访问条件。本方案不做 DNS 查询、服务器抓取、重定向跟踪、IP 网段或完整 SSRF 防护。与媒体上传、任意规则相比，复用现有规范化和事务边界更容易验证；这些是 Agent 的产品取舍。

## 独立管理资源

key `security.target_host_allowlist`，默认 `{"enabled":false,"hosts":[]}`。

- GET `/api/v1/admin/system/target-host-allowlist` 返回 `{enabled,hosts,updatedAt}`。
- POST `/api/v1/admin/system/target-host-allowlist/update` 接受 `{enabled,hosts,expectedUpdatedAt}`，返回同一资源。
- 32768 B 上限；三个字段必需且非 null；未知／重复字段、错误类型、尾随 JSON、非法媒体类型、查询参数整体拒绝。enabled 必须为 JSON boolean。
- 管理输入 hosts 0–100 项；enabled=true 要求至少 1 项。使用既有 normalizeHosts 的完整规范化边界。disabled 仍校验 canonical 存储，不以关闭为由掩盖坏配置。
- 版本沿用 UTC RFC3339Nano、微秒精度和完整回传；先 CAS 再 no-op。陈旧同内容仍冲突，真正 no-op 不改版本或审计。
- 管理输入错误 `900212`、冲突 `900213`；目标受限继续 `200121`；权限 `120001`；基础设施／缺行／坏存储为 HTTP500／`900000`。实施前再次核错误码未占用。
- 与黑名单相同的当前数据库身份及双权限、五秒 deadline、键名审计、no-store。不得记录列表、目标 URL 或原 JSON，旧 strict settings／公开 DTO 不变。

## 匹配及事务

关闭白名单时，只按原黑名单规则检查，不增加 URL 语法限制。启用后每个新目标必须为已验证的 DNS 主机并精确命中白名单；IP 分类所得空 host 必须拒绝为受限，不能当作白名单匹配。Unicode 目标由现有 IDNA 转 ASCII 后匹配，管理输入只接受 ASCII／有效 ACE。大小写及一个终止点规范化，端口／scheme／path／query／fragment 不参与主机比较；URL 存储原文不变。

黑名单优先，两表重叠的主机仍被拒绝；不为重叠自动改写任一资源。帮助文案明确此优先级。语法分类错误仍为原非法目标，不能降为未命中放行。

沿用 `internal/targetpolicy` 双 int32 gate `(0x4d4f4555,0x54504f4c)`。两种管理保存先 exclusive，再当前 actor／group share，再对应 setting FOR UPDATE；目标写入先 shared，再既有业务锁。在同一 gate 持有事务中逐次读取两个合法 canonical 资源，不增加跨请求缓存。不同策略的并发保存也串行，避免读到保存中间态；不承诺两个独立提交成为一次原子管理操作。

四个 service 路径继续覆盖七个 HTTP 协议：单条 Create、统一四种批量、本人 Update、AdminUpdate。原授权先于目标内容泄漏；回执在当前身份重查后、策略前恢复，同 key 异内容仍冲突。批量任何一项受限整批回滚。更新省略目标或锁内与原目标字节相同不触新限制；改变 path／query 也算实际新目标。公开 open／preview／unlock／continue 完全不读策略。

## 后端结构、迁移与回退

在 targetpolicy 新增 allowlist 的 model／strict JSON／service／handler，复用 host 规范化、版本校验、身份辅助和 gate；旧管理协议保持原字段和错误码。CheckTargets 读取并执行两个资源，启动验证也检查两个资源。App／router 注入独立新管理 handler，不生成新固定短码入口。

新迁移使用正式启动时确认的下一个序号，插入默认 off、on conflict do nothing，新增只记录 allowlist key 的 audit trigger。Down 只卸新 trigger／function，保留资源、版本及历史，再 Up 不覆盖；旧应用回退忽略新 key，不能声称白名单仍生效。

优先复用 SQLC 既有 GetSystemSetting／UpdateSystemSettingValue 与当前 targetpolicy 身份查询；未修改 SQLC 输入时不重复生成。若实施中确需改查询，则通过锁定 1.30 标准入口生成并核完整输入／输出零漂移，不手改生成文件。

## 前端

新增独立 entity／draft／editor，AdminSettings 原 general form 外单独卡片。共享既有 host scalar 校验，不为两种资源建立通用 CRUD 框架。草稿含 enabled、host 行和完整版本；关闭不清列表，清空不暗关 enabled，启用空表显示明确双语错误。所有操作仍需最终显式保存。

保留行顺序和编辑焦点，保存后才使用服务端规范排序。加载失败、保存失败、冲突和权限不足分别反馈；冲突保草稿、禁止自动重试，仅显式重载解除。默认尚未加载前不开放开关或保存。

独立 query key 及身份 scope／generation 同步清理私有状态；切号、同号重登录、撤权、卸载令所有 load／save success、error、finally 失效。edit revision 阻迟到读取覆盖编辑。缓存不能闪回旧账号文档。

目标受限复用既有 `200121` 各入口消息，仍验证单条、四批量、本人和后台编辑真实行为。先 unknown 后确定拒绝仍 unknown，payload／UUID 不变；首次确定拒绝才可回编辑，不能用新策略推断先前未提交。

## 验证与交付

先用现有 App 真实新 GET 观察缺端点 `100001`，再用 fixture 插入开启白名单让现有创建仍放行作为真实缺限制 RED。编译／fixture／安装错误不算产品 RED。

单元及真实 PG 覆盖 false 默认兼容、true 空拒绝、100／101、完整 JSON 和 CAS、ACE／Unicode／尾点／IP、deny 优先、七协议原子性、回执恢复与授权先后、两个策略共享 gate 的真实队列、取消／撤权／审计回滚和迁移往返。并发用可观察队列／确定性同步，不用固定 sleep。

前端先观察缺卡片行为 RED，再实现；严格 entity、enabled 与行编辑、冲突、双语、所有异步守卫和 unknown 语义具名验证。完整必要本地门禁及准确新产品／双语桌面手机浏览器、原图和精确 cleanup 取证；最终唯一独立终审和真实 CodeRabbit 都覆盖实际最终候选，不查 CI，不发布部署。容量和用完恢复清理按仓库既定规范。
