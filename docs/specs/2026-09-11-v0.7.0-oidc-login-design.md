# v0.7.0 多提供商 OIDC 登录设计

## 1. 背景

MoeURL 当前只有本地用户名和密码登录，但账号、用户组、动态权限、Cookie Session、用户禁用和生产部署边界已经稳定。OIDC 应接入这些既有能力，而不是建立第二套用户、权限或会话系统。

稳定规格已经提出多提供商、登录页入口、默认用户组和后续禁用本地登录的目标。本版本先完成可独立使用的多提供商登录闭环；系统设置、账号合并和企业目录同步继续保持独立边界。

## 2. 方案比较

### 2.1 单提供商环境变量配置

实现最小，但每次修改都要重启服务，无法管理多个提供商，也无法自然承载启停、Secret 保留和并发更新。该方案不符合现有多提供商产品目标。

### 2.2 数据库管理的多提供商 OIDC

管理员通过真实页面管理提供商，敏感字段加密保存，登录协议与本地 Session 汇合。实现面较大，但能形成完整产品闭环，并为后续模板、禁用本地登录和账号绑定留下清晰扩展点。

### 2.3 只建立认证适配器，不开放真实登录

代码改动较小，但用户无法获得新能力，协议安全也没有端到端验证，不应作为独立产品版本。

本设计采用方案 2.2。

## 3. 信任边界

```text
Browser
  │ same-site start/callback
  ▼
MoeURL
  │ HTTPS discovery/token/JWKS
  ▼
Configured OIDC Provider
```

- 部署管理员可信，可以配置 Issuer；普通用户不能影响服务端请求目标。
- `MOEURL_PUBLIC_BASE_URL` 是回调地址的唯一来源，不信任请求 `Host` 或转发头拼接回调地址。
- 授权码、Token、Client Secret、PKCE verifier、`state` 和 `nonce` 不写入日志。
- 浏览器持有随机 `state` 和按 state 隔离的短期关联 Cookie；服务端数据库只保存两者摘要及加密后的 verifier。
- OIDC 最终身份只由经过签名验证的 ID Token 提供，不信任查询参数或未经验证的 UserInfo 响应。

## 4. 配置契约

新增应用配置：

```text
MOEURL_PUBLIC_BASE_URL=https://links.example.com
MOEURL_OIDC_ENCRYPTION_KEY=<base64-encoded 32 bytes>
```

`MOEURL_PUBLIC_BASE_URL` 规范化时去除末尾 `/`，并拒绝用户信息、查询、片段和非根路径。生产环境只允许 HTTPS；开发环境允许 `http://127.0.0.1`、`http://localhost` 和 `http://[::1]`。

`MOEURL_OIDC_ENCRYPTION_KEY` 解码后必须正好 32 字节。未配置 OIDC 时两个变量可以为空，保持现有部署兼容；管理员尝试创建或启用提供商时，任一配置缺失均返回明确但不泄密的业务错误。应用读取到已启用提供商但无法构造安全 OIDC 运行时，应拒绝启动，避免页面展示不可用登录方式。

密钥必须与数据库备份分开保存。丢失密钥后既有 Client Secret 和未完成登录尝试无法恢复；恢复流程必须同时恢复同一密钥。首版不提供在线换钥。

## 5. 数据模型

### 5.1 `oidc_provider`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `uuid` | 主键。 |
| `key` | `text` | 唯一、不可变，小写字母数字及单横线，首尾必须为字母数字。 |
| `display_name` | `text` | 非空，面向登录页。 |
| `issuer_url` | `text` | 非空、绝对 HTTPS；开发环境回环 HTTP 仅由服务校验允许。 |
| `client_id` | `text` | 非空。 |
| `client_secret_ciphertext` | `bytea` | AES-256-GCM 版本化密文。 |
| `authorization_endpoint` | `text` | Discovery 校验后的地址。 |
| `token_endpoint` | `text` | Discovery 校验后的地址。 |
| `jwks_uri` | `text` | Discovery 校验后的地址。 |
| `allowed_email_domains` | `jsonb` | 非空、去重、规范化后的精确域名数组。 |
| `enabled` | `boolean` | 是否公开并允许登录。 |
| `created_at` / `updated_at` | `timestamptz` | 审计与乐观并发。 |
| `deleted_at` | `timestamptz` | 软删除。 |

Provider `key` 一旦创建不可修改。软删除后保留唯一性，防止旧外部身份被同名新配置接管。

### 5.2 `external_identity`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `provider_id` | `uuid` | 引用 `oidc_provider`。 |
| `subject` | `text` | 非空，与 provider 组成主键。 |
| `user_id` | `uuid` | 引用 `app_user`，删除用户时级联删除绑定。 |
| `created_at` / `last_login_at` | `timestamptz` | 登录归属与最近使用时间。 |

同一用户在同一 provider 下至多绑定一个 subject。`subject` 不进入公开 API 或普通日志。

### 5.3 `oidc_login_attempt`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `state_hash` | `bytea` | 主键，SHA-256 摘要。 |
| `provider_id` | `uuid` | 引用 provider。 |
| `nonce_hash` | `bytea` | SHA-256 摘要。 |
| `browser_binding_hash` | `bytea` | 发起浏览器关联令牌的 SHA-256 摘要。 |
| `verifier_ciphertext` | `bytea` | 加密 PKCE verifier。 |
| `return_path` | `text` | 已验证的站内相对路径。 |
| `expires_at` / `created_at` | `timestamptz` | 五分钟有效期和清理依据。 |

回调通过单条 `DELETE ... RETURNING` 原子消费尝试。任何回调结果都不能恢复已经消费的状态。

## 6. 提供商管理

API：

```text
GET  /api/v1/admin/oidc/provider/list
POST /api/v1/admin/oidc/provider/create
POST /api/v1/admin/oidc/provider/update
POST /api/v1/admin/oidc/provider/delete
```

所有操作在 Service 层再次校验 `admin:access`。列表不返回 Secret，只返回 `clientSecretConfigured`。更新使用：

```json
{
  "id": "uuid",
  "displayName": "Company SSO",
  "issuerUrl": "https://id.example.com",
  "clientId": "moeurl",
  "clientSecret": { "mode": "preserve" },
  "allowedEmailDomains": ["example.com"],
  "enabled": true,
  "expectedUpdatedAt": "2026-09-11T00:00:00Z"
}
```

替换 Secret 使用 `{ "mode": "set", "value": "..." }`。不支持从已配置状态清空 Secret；要停止使用应停用或删除 provider。

创建、修改 Issuer/Client ID/Secret 或从停用切换为启用时执行 Discovery。使用保留 Secret 重新启用时，还必须先以当前部署密钥验证既有密文。要求响应中的 `issuer` 与规范化输入完全一致，并要求授权、Token 和 JWKS 端点为 HTTPS；开发环境只对同一回环主机放宽 HTTP。网络、JSON 和协议校验使用有界 Context，OIDC HTTP Client 不自动跟随重定向，并限制协议响应体大小，避免已校验端点转发敏感请求或返回无界内容。

应用启动时读取全部已启用 provider，并验证必要运行字段、邮箱域名配置和 Client Secret 密文可用。只要任一 provider 无法使用当前部署密钥解密，应用就拒绝启动，避免公开不可用的登录入口。

更新 SQL 同时比较 `updated_at`。不匹配返回冲突和最新 provider，前端保留当前草稿，不自动重放写入。

## 7. 登录状态机

### 7.1 登录方式

```text
GET /api/v1/auth/methods
```

返回 `local.enabled=true` 和已启用、未删除 provider 的 `key`、`displayName`。不返回 Issuer、Client ID、邮箱域名或其他管理配置。

### 7.2 开始登录

```text
GET /api/v1/auth/oidc/{providerKey}/start?returnTo=/console
```

流程：

1. 读取已启用 provider 并解密 Secret 可用性。
2. 校验 `returnTo` 为以单 `/` 开始、不含 scheme、host、反斜线和控制字符的站内路径；无效值回退 `/console`。
3. 生成至少 256 bit 的 `state`、`nonce`、PKCE verifier 和浏览器关联令牌。
4. 在数据库写入 state、nonce 和浏览器关联令牌的摘要，以及加密 verifier、provider 和 5 分钟过期时间。
5. 将浏览器关联令牌写入按 state 隔离、仅覆盖对应 callback 路径的 `HttpOnly`、`SameSite=Lax` 短期 Cookie；生产环境同时设置 `Secure`。
6. 使用 `S256` challenge、`openid email profile` scope 和固定回调地址生成授权 URL。
7. 返回 `302`，并设置 `Cache-Control: no-store`。

### 7.3 回调

```text
GET /api/v1/auth/oidc/{providerKey}/callback?code=...&state=...
```

流程：

1. 对 state 计算摘要并通过 `DELETE ... RETURNING` 原子消费尝试。
2. 对 callback Cookie 中的浏览器关联令牌计算摘要，并与已消费记录常量时间比较；缺失、错误或来自另一浏览器时关闭失败。
3. 无论 callback 成功或失败，都删除本次 state 对应的浏览器关联 Cookie。
4. 校验尝试未过期且 provider 与路径一致。
5. 解密 verifier，使用固定 redirect URI 交换授权码。
6. 要求 Token 响应包含 ID Token；校验签名、Issuer、时间声明，并要求 Audience 仅包含当前 Client ID；存在 `azp` 时也必须等于当前 Client ID。
7. 对 ID Token nonce 计算摘要并与尝试记录常量时间比较。
8. 解析 `sub`、`email`、`email_verified`、`name` 和 `preferred_username`。
9. 在事务中查找或创建外部身份及本地用户，重新检查 provider 和本地用户状态。
10. 创建现有 Session Cookie，并以 `303` 跳转到保存的站内路径。

预期协议失败统一跳转 `/login?oidcError=<bounded-code>`；基础设施错误记录安全分类后跳转通用错误。URL 不包含外部错误描述、Token 或身份声明。

## 8. 账号供应规则

既有 `(provider_id, subject)` 绑定优先，邮箱不再参与访问判断。首次身份必须满足：

- `sub` 非空且长度受限。
- `email` 语法有效。
- `email_verified` 严格为 `true`。
- 邮箱域名经小写和 IDNA 规范化后精确匹配 provider 白名单。

首次创建始终加入内置 `user` 组。用户名格式：

```text
oidc-{provider-key}-{base32(sha256(subject)) 前 20 个字符}
```

该名称稳定、无外部 PII 且冲突概率足够低；数据库唯一冲突时重新读取相同 provider/subject 绑定，不生成随机替代身份。昵称使用第一个合法的标准声明，经过 Unicode 字符长度和空白规范化；都不可用时使用 provider 显示名称加“用户”的本地化无关回退。

系统不按邮箱连接既有账号。未来账号绑定必须要求同时证明本地 Session 和外部身份，另行设计。

## 9. 加密与敏感数据

密文格式包含固定版本字节、随机 12 字节 nonce 和 AES-GCM sealed payload。附加认证数据（Additional Authenticated Data，AAD）使用统一字节格式隔离用途和记录，避免密文跨用途或跨记录替换：

```text
v1 | nonce | ciphertext+tag
AAD = "moeurl:oidc:" + purpose + NUL + record-id
```

provider Secret 的 `purpose` 为 `provider-secret`，`record-id` 为 provider UUID。登录 verifier 的 `purpose` 为 `login-verifier`，`record-id` 为 state hash 的 Base64URL 无填充编码。所有解密错误返回稳定哨兵错误，日志只记录操作、provider key、request ID 和错误分类。

前端 Secret 输入沿用敏感字段边界：不放入查询数据、Mutation variables、成功反馈或长期响应；明文只保存在短期 `WeakMap` 中，在请求调用边界读取，并在 settled 后清理。

## 10. 并发、清理与失败语义

- provider 更新通过 `updated_at` 乐观并发。
- 外部身份创建依赖数据库唯一约束，并在事务内处理首次登录竞争。
- 登录尝试只能原子消费一次；失败回调也不会恢复。
- 每分钟清理过期 attempt，每周期最多四批、每批 500 条，少于一批时提前结束。
- OIDC start 与 callback 各使用独立有界进程槽位，防止大量请求占满数据库和外部 HTTP 连接。
- 反向代理继续对 start/callback 做来源级限流；应用不信任任意客户端 IP Header。

业务错误保持 HTTP `200` 的 API 约定；浏览器 start/callback 使用标准重定向响应。未知基础设施错误不得出现在响应、Location 或日志属性中。

## 11. 前端状态

登录页：

- 登录方式加载中时本地表单仍可用，OIDC 区域使用稳定占位高度。
- 无 provider 时不显示分隔区域。
- provider 入口使用图标加显示名称，点击后进行完整页面导航。
- 回调失败返回登录页后显示一次可理解错误；不展示上游错误文本。

管理员页面：

- 列表与编辑器不嵌套卡片，使用紧凑列表和单一编辑区域。
- 新增和编辑时明确标识 Secret 已配置、保留或替换。
- 切换 provider 时清除上一项成功与错误反馈。
- 保存期间锁定当前草稿；冲突时同步最新数据但保留冲突目标草稿。
- 删除需要确认，成功后选择下一个可用 provider；空列表展示可执行的新增入口。

## 12. 路由与缓存

- `/api/v1/auth/methods`、start、callback、管理员 API 均设置 `Cache-Control: no-store`。
- start/callback 在静态 fallback 和 `/{slug}` 之前注册。
- `/admin/setting` 继续由管理员路由守卫保护并承载身份认证设置；导航去除“规划中”状态。
- Service Worker 不缓存 OIDC 或身份 API，也不拦截跨域 IdP 导航。

## 13. Migration 与回滚

Up 在单一事务中创建三张表、约束和清理索引。表创建不改写既有用户、Session 或权限。

Down 首先检查 `external_identity` 是否为空。存在绑定时抛出明确错误并保持 schema 不变；为空时按依赖顺序删除 attempt、identity 和 provider。这样测试环境和未启用部署可完整回滚，已投入使用的部署不会静默丢失登录归属。

应用版本回退应优先保留新表并运行旧应用；旧应用忽略 OIDC schema，本地登录保持可用。只有确认没有外部身份后才执行 migration Down。

## 14. 测试策略

- migration：Up、约束、无身份 Down、已有身份拒绝 Down、清理后重试和 reapply。
- 加密：随机 nonce、AAD 隔离、错误密钥、截断密文和敏感值不泄露。
- Discovery/协议：Issuer 不匹配、端点不安全、超时、PKCE、state、nonce、签名、audience 和过期。
- Service：权限、CRUD、Secret 保留、冲突、软删除、域名策略、首次供应、重复登录、禁用用户和并发首次登录。
- Handler/Router：固定路由优先级、Cookie、安全重定向、no-store、日志脱敏和业务错误。
- 前端：Schema、防缓存数据边界、登录方式状态、管理页面全状态和 Secret 清理。
- E2E：本地测试 IdP 下的管理员配置、首次 OIDC 登录、重复登录、域名拒绝、provider 停用和本地登录回归。
